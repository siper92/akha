# Akha - major questions (human)

Decisions that shape the platform. Answer before implementation starts.

## 1. scope and product

- what is the v1 goal: a single-user local tool, a team tool, or a multi-tenant service?
 - works locally but can be deployed to a server for multiple hosts
   - always has the server local or remote, configured via `config.yaml` or env vars
   - workers can run on the same host or on remote hosts
- which n8n / temporal features are in v1: triggers, schedules, retries, durable state, UI?
  - for now nothing just focus on interfaces and language design
- is a workflow only a `.ak` script?
  - always a `.ak` script, this version is only a language and interpreter focused
- who writes `.ak` scripts: humans, AI, or both?
  - both, for now focus on the sec file and the language design, later the script will be generated by AI and dynamically interpreted
    - in the version 2, flows can be downloaded from the backend and executed by the worker
- what is the success criteria for v1 (one demo workflow end to end?)
  - execute a `.ak` script on the worker, focusing on the spec - small implementation language features ergonomics and design first

## 2. topology

- how many workers per backend in v1: one, a few, hundreds?
  - it dosent matter, backend issues tokens to workers that have access token for it
    - access token is configured
- do workers run on trusted machines only, or on untrusted user hosts?
  - workers authenticate with the backend, run everywhere
- does the worker pull work from the backend, or does the backend push work?
  - v1 - backend only issues tokens - JWT to workers, workers can validate them
    - this is done to integrate the protobuf generator in the backend and worker
- can a worker run offline and sync later?
  - for now, no - workers must obtain a valid token 
- is the backend a single binary, or split into services (auth, llm, logs, scheduler)?
  - for now single binary, but can run it own workers 
    - this means 2 tears of tokens (backend and worker) 
    - backend issues tokens to workers, workers can validate them
    - backend starts workers as go routines 
      - so it gives them privileges to run jobs and access the backend data
    

## 3. security

- how is a worker registered the first time (static token in config, one-time invite code, mTLS)?
  - _defs/proto/auth.proto - define a proto for the worker to register with the backend, and validate a JWT token
- JWT lifetime and refresh strategy: short lived, no refresh just new login always for expired tokens
  - configured from config.be.yaml
- signing: symmetric (HS256) or asymmetric (EdDSA / RS256) keys? who holds the keys?
  - the keys are in the BE config, and the backend signs the JWT tokens for workers
- what can a worker read/write on its host: whole FS, a sandbox dir, per workflow allow list?
  - determined by the `.ak` script
- are LLM API keys stored only in the backend, never sent to workers?
  - only backend talks to LLM's
- backend logs every login attempt, for v1 to validate
- use middleware to validate JWT tokens on every gRPC call from workers

## 4. the language (.ak)

- build an own interpreter, or embed starlark and expose `Ak` / `FS` as modules?
  - we are bulding a new interpreter, but we can use starlark as a reference for the language design
- is the language statically checked before execution, or only at runtime?
  - it's a script language, so we can do static checks for every evecution
- how are LLM calls exposed in the language (new `AI` namespace)?
  - this is not for v1, but we can add a new namespace for LLM calls via backend calls from worker on parsed AI.* module
- what other namespaces are planned after `Ak` and `FS` (HTTP, Shell, Git, Env)?
  - this is not for now, this version is focused on the language design and interpreter, 
    - but we can add new namespaces for HTTP, Shell, Git, Env later easy so desing is important
  - focus on setup and development ergonomics first, commands, tests and such must be easy to write
- is `Ak.Allow` a hard permission check or a declaration only?
  - it includes the modules that can be used in the script
  - all modules are accessible, but the script must declare which modules it to use
- are scripts versioned and stored in the backend, or only on the worker host?
  - script are interpreted on the worker, but there is in interpreter interface and runner that can accept strings

## 5. AI / LLM integration

NOT for this version

## 6. storage and data

- database: stay on sqlite, or plan for postgres from the start?
  - slqite is enough for now, both backend and worker use it
- what is stored: tokens, workers, workflows, runs, steps, logs, templates, artifacts?
  - tokens are files in a cache dir, provide a good cache implementation for it and interface
    - cache is used on worker and backend
- how long are logs and run history kept?
  - as long as the files, v1 - deletes are handler by justfile and scripts
- where do large outputs go (db, filesystem, object storage)?
  - _env/.cache/*

## 7. APIs

- worker to backend: gRPC only (already started) or also HTTP?
  - for now focus on gRPC only, use the genenrated key - check the docker to setup the gRPC server and client
- is GraphQL needed in v1, and for whom (UI, CLI, external clients)?
  - for now, no GraphQL,
- is there a CLI (`akha`) for humans, and which commands (run, deploy, logs, login)?
  - use the ahka is the root command 
    - use akha backend for backend commands,
    - akha worker for worker commands
- is a web UI planned, and when?
  - don't thonk for now, focus on the language design and interpreter, but we can add a web UI later

## 8. operations

- how are backend and worker deployed (docker, single binary, systemd)?
  - running as a single binary, with flags for relevant stuff, config first for most run time options
- observability: structured logs only, or metrics + tracing (OpenTelemetry)?
  - use standard logging for now, but we can add OpenTelemetry later
- config: `config.yaml` + env vars via viper, secrets from where?
  - use viper
- upgrade policy: must old workers keep working with a newer backend?
  - workers are never upgraded new ones are started, as do backends

## 9. process

- priority order of milestones (see plan.md) - agree or change?
- test expectations: unit only, or integration tests with a real backend + worker?
  - focus on unit test for the language and parser, but we can add integration tests later
- what is out of scope for v1 explicitly?
  - everything that is not related to the language design and interpreter
  - minimal features are better
